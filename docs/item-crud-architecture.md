# Item CRUD Architecture

A design for one unified create/read/update/delete system serving all seven item
types — mutations in a single action file, reads in `lib/db` called straight from
server components, one dynamic route, and shared components that adapt by type.

> Generated by `/research item-crud-research`. **This is a design document, largely
> not a record of shipped code.** It is proposed against the conventions already
> established in `src/actions/profile.ts`, `src/lib/db/*`, `src/lib/auth-schemas.ts`
> and the dashboard components.
>
> **Steps 1–4 of §10 have since shipped** — the proxy matcher, `getItemTypeBySlug`,
> `getItemsByType` and the `/items/[slug]` list page — with the differences noted
> there. Everything else (the drawer, the form, `src/actions/items.ts`,
> `src/lib/item-schemas.ts`, the shadcn additions, the upload route) is still design
> only, and the read-only slice was built without the `ItemList` / `ItemsEmptyState`
> components §2 proposes.
>
> Two listed sources do not exist: **`docs/content-types.md`** (the item-type
> reference is at [`docs/item-types.md`](item-types.md)) and
> **`src/lib/constants.tsx`** (there is no constants module — type metadata lives
> in `ItemType` rows; the only code-side lookups are `src/lib/icons.ts` and
> `src/lib/pro.ts`). Both were substituted.

## 1. The governing idea

From [`docs/item-types.md`](item-types.md): **an item type is a database row, not a
TypeScript constant.** Its icon, color, label and route slug are columns. The seven
system types differ from each other in exactly two ways that code can see:

1. **`contentKind`** — `TEXT` (4 types) / `URL` (1) / `FILE` (2). This decides which
   `Item` columns are populated.
2. **`name`** — only used to decide Pro gating (`file`, `image`).

Everything else — title, description, tags, collections, pin, favorite, search — is
identical across all seven (`Item`, `prisma/schema.prisma:123-158`).

So the system needs **three shapes, not seven**. Every branch below keys on
`contentKind`, never on the type name. A seventh type added tomorrow, or a user's
custom type added post-MVP, flows through unchanged as long as it declares one of the
three kinds.

> **The one exception is Pro gating**, which keys on `name` because "which types are
> Pro" is a product decision rather than a per-row fact — see `src/lib/pro.ts:1-10`
> for why that list deliberately lives in code.

```
│   └── db/
│       ├── items.ts                EXTEND — add getItemsByType, getItem
│       └── item-types.ts           EXTEND — add getItemTypeBySlug
├── app/(app)/items/[type]/
│   ├── page.tsx                    NEW — the one dynamic route
│   └── not-found.tsx               NEW — unknown slug
├── components/items/
│   ├── ItemList.tsx                NEW — server, reuses dashboard/ItemCard
│   ├── ItemDrawer.tsx              NEW — client, Sheet shell
│   ├── ItemForm.tsx                NEW — client, the shared envelope
│   ├── ItemContentFields.tsx       NEW — client, THE contentKind switch
│   ├── ItemRowActions.tsx          NEW — client, pin/favorite/delete
│   └── ItemsEmptyState.tsx         NEW — server
└── proxy.ts                        EDIT — add /items/:path* to the matcher
```

This follows `context/coding-standards.md` § File Organization exactly: mutations in
`src/actions/[feature].ts`, components in `src/components/[feature]/`, utilities in
`src/lib/`.

### The split, and why it is where it is

| Concern | Lives in | Reason |
|---|---|---|
| Reads | `src/lib/db/items.ts` | Server components fetch directly with Prisma — no action round trip for data that renders on the server anyway |
| Writes | `src/actions/items.ts` | Client forms cannot touch Prisma; a Server Action is the only write path |
| Validation | `src/lib/item-schemas.ts` | Shared by every action, the way `auth-schemas.ts` is shared by five |
| Per-type rendering | `src/components/items/ItemContentFields.tsx` | One file, one `switch`, three branches |
| Per-type metadata | the `ItemType` row | Already there |

**File uploads are the one exception to "mutations go in actions."**
`context/coding-standards.md` explicitly routes file uploads with progress tracking to
API routes. `file` and `image` items therefore need
`src/app/api/items/upload/route.ts` to push the blob to Cloudflare R2 and hand back an
object URL, which the form then submits as an ordinary field. That route is out of
scope here and is not required for the five non-file types.

## 3. How `/items/[type]` routing works

### The URL

The sidebar already links to `/items/${type.slug}` (`SidebarTypeNav.tsx:53`), so the
seven live URLs are fixed by the seeded slugs:

`/items/snippets` · `/items/prompts` · `/items/commands` · `/items/notes` ·
`/items/files` · `/items/images` · `/items/links`

> **Naming note:** the segment is `[type]` per the research brief, but the value it
> carries is a **`slug`**, not a `name` — `snippets`, not `snippet`. Naming the folder
> `[slug]` would match the column and remove a standing source of confusion. Either
> works; the resolver below is what matters.

### The page

```tsx
// src/app/(app)/items/[type]/page.tsx
import { notFound } from "next/navigation";

export const dynamic = "force-dynamic";

export async function generateMetadata({ params }: PageProps<"/items/[type]">) {
  const { type } = await params;
  const userId = await getCurrentUserId();
  const itemType = await getItemTypeBySlug(type, userId);

  return { title: itemType ? `${itemType.label} | Devstash` : "Not found" };
}

export default async function ItemsByTypePage({
  params,
}: PageProps<"/items/[type]">) {
  const { type } = await params;
  const userId = await getCurrentUserId();

  const itemType = await getItemTypeBySlug(type, userId);
  if (!itemType) notFound();

  const items = await getItemsByType(userId, itemType.id);

  return <ItemList itemType={itemType} items={items} />;
}
```

Four things are load-bearing:

1. **`PageProps<"/items/[type]">` is a generated global**, not a hand-written type
   (`CLAUDE.md` § Route component props). `params` is a **Promise** and must be
   awaited. The type does not exist until `next dev` or `next build` regenerates
   `.next/types/routes.d.ts` — so the first `tsc --noEmit` after creating the folder
   will fail until the dev server has run once.

2. **`getItemTypeBySlug` is user-scoped**, not a bare `findUnique`. A custom type
   belongs to one user, so the lookup must be
   `WHERE slug = :slug AND (userId IS NULL OR userId = :userId)` — the same predicate
   `getItemTypes()` already uses (`src/lib/db/item-types.ts:51`). Without the scope,
   one user's custom slug would resolve for everyone.

3. **`notFound()` on an unresolved slug**, so `/items/nonsense` is a 404 rather than an
   empty list that looks like a working page.

4. **`export const dynamic = "force-dynamic"`**, matching
   `src/app/(app)/dashboard/page.tsx`. The page reads per-user data on every request
   and must never be prerendered.

### ⚠️ The proxy matcher must be updated

`src/proxy.ts` currently matches only `["/dashboard/:path*", "/profile/:path*"]`. Until
`"/items/:path*"` is added, `/items/snippets` is a **public route**, and
`getCurrentUserId()` will throw the error it was written to throw:

> `No signed-in user. This route is missing from the 'src/proxy.ts' matcher.`
> — `src/lib/db/user.ts:46-48`

Per `CLAUDE.md`: *"a new private route needs adding there."* This is the single
easiest step to forget and the only one that fails as a crash rather than a bug.

### One route, not seven

Seven hard-coded routes would be seven copies of the same page differing only in a
constant — and would still not serve custom types, which have no known slug at build
time. One dynamic route serves the seven system types *and* every future custom type
with no new code.

## 4. Data fetching — `src/lib/db/`

Reads never go through a Server Action. Server components call these directly, as
`RecentItems.tsx` and `DashboardStats.tsx` already do.

### Additions to `src/lib/db/item-types.ts`

```ts
/** One item type by its route slug, scoped to what this user may see. */
export async function getItemTypeBySlug(
  slug: string,
  userId: string,
): Promise<ItemTypeDetail | null>;
```

Returns `id`, `name`, `label`, `slug`, `icon`, `color`, `contentKind`. Note it must
return **`contentKind`**, which the existing `ITEM_TYPE_SELECT` does not include — that
select is deliberately minimal (id/label/icon/color) because it is embedded in every
item and collection card. Widening it would drag `contentKind` through queries that do
not need it; a second, wider select is the right call.

### Additions to `src/lib/db/items.ts`

```ts
/** Every item the user filed under one type, newest first. */
export function getItemsByType(
  userId: string,
  itemTypeId: string,
): Promise<ItemSummary[]>;

/** One item in full, for the detail drawer and the edit form. */
export function getItem(userId: string, id: string): Promise<ItemDetail | null>;
```

`getItemsByType` is nearly free: the private `findItems()` helper
(`src/lib/db/items.ts:53-87`) already takes a `where` and returns `ItemSummary`. Adding
an optional `itemTypeId` to that filter is a one-line change, and the new function is a
three-line wrapper — the same shape as `getPinnedItems` and `getRecentItems`.

`ItemDetail` extends `ItemSummary` with the storage columns the card omits:
`content`, `language`, `url`, `fileUrl`, `fileName`, `fileSize`, `contentType`, plus
the collections it belongs to.

**`getItem` takes `userId` and puts it in the `where`, not in a post-fetch check.** A
wrong owner then produces `null` → `notFound()`, so the URL cannot be used to probe
which item ids exist. A 403 would confirm existence; a 404 confirms nothing.

## 5. Mutations — `src/actions/items.ts`

One file, `"use server"` at the top, following `src/actions/profile.ts` throughout.

```ts
export async function createItem(prev: ItemFormState, formData: FormData): Promise<ItemFormState>;
export async function updateItem(prev: ItemFormState, formData: FormData): Promise<ItemFormState>;
export async function deleteItem(prev: DeleteItemState, formData: FormData): Promise<DeleteItemState>;
export async function toggleItemPinned(itemId: string): Promise<ToggleState>;
export async function toggleItemFavorite(itemId: string): Promise<ToggleState>;
```

The first three are `useActionState`-shaped (`(previousState, formData) => newState`).
The two toggles take a plain id — they are fired from a button, not a form, and have
no field errors to report.

### The five rules every mutation follows

**1. Re-derive the user from `auth()`; never read an id from `FormData`.**

This is the project's hardest rule (`CLAUDE.md`: *"A Server Action is a public
endpoint. Being rendered behind the proxy is not authorization"*).
`src/actions/profile.ts:19-26` is the reference implementation — a `currentUserId()`
helper and a shared `NO_SESSION` message. `src/actions/items.ts` should have the same
pair rather than importing them, or they should move to a shared module; duplicating
the sentence is how the two copies drift.

**2. Validate with Zod before touching Prisma.** `safeParse`, then
`z.flattenError(parsed.error).fieldErrors` on failure — exactly
`src/actions/profile.ts:74-82`.

**3. Scope the write itself, don't read-then-write.**

```ts
// Right — one atomic statement; a wrong owner updates 0 rows.
const { count } = await prisma.item.updateMany({
  where: { id, userId },
  data,
});
if (count === 0) return { error: "That item no longer exists." };
```

`prisma.item.update({ where: { id } })` after a separate ownership `findUnique` has a
window between the two. `updateMany`/`deleteMany` with `userId` in the `where` closes
it and needs no second query. The count is the authorization result.

**4. Validate the submitted `itemTypeId` — this is a real authz hole.**

`itemTypeId` arrives from the form, and `Item.itemTypeId` is a plain FK with no
scoping. Without a check, a crafted submit can file an item under **another user's
custom type**, which would then render that user's label and color in the attacker's
sidebar and count toward the wrong type. The action must confirm the referenced type is
a system type (`userId: null`) or owned by the caller — the same predicate as
`getItemTypeBySlug`. It needs that row anyway, to read `contentKind`.

**5. Revalidate after every write.**

```ts
revalidatePath(`/items/${itemType.slug}`);
revalidatePath("/dashboard");
```

Both pages are `force-dynamic`, so this is not about the Full Route Cache — it is about
the **client-side Router Cache**, which would otherwise serve a stale list when the user
navigates back to a page they already visited in this session. A sidebar count that
lags one item behind is exactly this bug.

### Return shape — resolved

This section originally flagged a conflict: `context/coding-standards.md` mandated a
`{ success, data, error }` wrapper that **no action in the codebase used**. The
recommendation was to follow the code rather than the doc, since a wrapper would make
every form unwrap a level for no gain.

**The standards doc has since been changed** to describe the flat shape, so there is no
longer a conflict to resolve — `src/actions/items.ts` should return a flat state object
like every existing action.

```ts
export interface ItemFormState {
  error?: string;
  fieldErrors?: Partial<Record<ItemFormField, string[]>>;
  message?: string;
  /** Changes on every success, so an effect can reset the form —
      see ChangePasswordState.succeededAt for why a message is not enough. */
  succeededAt?: number;
}
```

That `succeededAt` field is not incidental: `src/actions/profile.ts:33-39` documents
the bug it fixes — a success message is the same string every time, so an effect
depending on it alone skips the reset on a second consecutive success.

### Why type-specific logic does *not* live here

The actions never ask "is this a snippet?". They ask the type row what `contentKind` it
declares and pick the matching schema:

```ts
const schema = itemSchemaFor(itemType.contentKind);   // TEXT | URL | FILE
const parsed = schema.safeParse(Object.fromEntries(formData));
```

Three branches, chosen by data, resolved inside `src/lib/item-schemas.ts`. Adding an
eighth type changes no action code.

## 6. Validation — `src/lib/item-schemas.ts`

Modeled on `src/lib/auth-schemas.ts`: shared fragments composed into per-case schemas,
so a rule cannot apply to create but not update.

```ts
/** Everything every item carries, regardless of type. */
const itemBase = z.object({
  itemTypeId: z.string().min(1),
  title: z.string().trim().min(1, "Title is required").max(200),
  description: z.string().trim().max(500).optional(),
  tags: z.array(z.string().trim().min(1)).max(20).default([]),
  collectionIds: z.array(z.string()).default([]),
  isPinned: z.coerce.boolean().default(false),
  isFavorite: z.coerce.boolean().default(false),
});

const textItem = itemBase.extend({
  contentType: z.literal("TEXT"),
  content: z.string().min(1, "Content is required"),
  language: z.string().trim().max(40).optional(),
});

const urlItem = itemBase.extend({
  contentType: z.literal("URL"),
  url: z.url("Enter a valid URL"),
});

const fileItem = itemBase.extend({
  contentType: z.literal("FILE"),
  fileUrl: z.url(),
  fileName: z.string().min(1),
  fileSize: z.coerce.number().int().positive(),
});

export const itemSchema = z.discriminatedUnion("contentType", [
  textItem, urlItem, fileItem,
]);

export function itemSchemaFor(kind: ItemContentKind) { /* three-way lookup */ }
```

**Why a discriminated union rather than one wide optional-everything schema:** it is
what makes the unused columns provably null. [`docs/item-types.md`](item-types.md) §3
notes that nothing in the schema enforces the kind→column mapping — every storage
column is nullable and `contentType` is a plain enum. A `link` with a stray `content`
value, or a `snippet` with a `fileUrl`, is a database the schema happily accepts. The
union is where that invariant actually gets enforced, so **the action must write the
non-applicable columns as explicit `null`** rather than omitting them, or an edit that
changes a type would leave the old kind's data behind.

Zod 4 is already a dependency (`zod@^4.4.3`); note `z.email()` / `z.url()` are
top-level in v4, as `auth-schemas.ts` uses them.

## 7. Components — responsibilities

`src/components/items/`. The rule: **exactly one file branches on `contentKind`.**

### `ItemList.tsx` — server

Header (type icon in `type.color`, `label`, count, "New" button), then a list of the
existing `ItemCard` (`src/components/dashboard/ItemCard.tsx`), or `ItemsEmptyState`
when there are none.

**Reuse `ItemCard`, do not fork it.** It already renders all seven types identically
from `type.icon` / `type.color` and takes `ItemSummary`, which is exactly what
`getItemsByType` returns. It lives under `dashboard/` for historical reasons; moving it
to `components/items/` would be tidier but touches four dashboard imports and is not
required.

### `ItemDrawer.tsx` — client

The slide-out shell. `context/project-overview.md` §3A is explicit: items are *"created
and viewed quickly inside a slide-out drawer, without a full page navigation."*
`src/components/ui/sheet.tsx` is already installed (pulled in by `sidebar`), so this is
a `Sheet` + `SheetContent side="right"` holding either the read view or `ItemForm`.

Owns open/closed state and nothing else. Type-agnostic.

### `ItemForm.tsx` — client

The shared envelope, identical for all seven types: title, description, tags,
collections, pin, favorite, submit. Wires `useActionState(createItem | updateItem, {})`
and renders `state.error` / `state.fieldErrors` in the established markup
(`ChangePasswordForm.tsx:72-88`).

Two details worth copying verbatim from `ChangePasswordForm`:
- a **separate `SubmitButton` component** calling `useFormStatus`, because the hook
  reads `pending: false` when called in the component that renders the `<form>`
  (`ChangePasswordForm.tsx:13-26`);
- a **`useEffect` keyed on `state.succeededAt`** to reset the form.

Delegates the varying middle to `<ItemContentFields contentKind={...} />` and knows
nothing about what that renders.

### `ItemContentFields.tsx` — client — **the only type switch**

```tsx
switch (contentKind) {
  case "TEXT":  return <><MarkdownOrCodeEditor name="content" /><LanguageSelect name="language" /></>;
  case "URL":   return <UrlField name="url" />;
  case "FILE":  return <FileUpload accept={accept} />;
}
```

Every per-type UI difference the product calls for collapses into these three branches:
the Markdown editor and syntax highlighting for text types, a URL field for `link`, an
upload control for `file`/`image`.

The one place `name` (not `contentKind`) may legitimately appear is `accept`:
`image/*` for `image`, unrestricted for `file`. Both are `FILE`, so `contentKind`
cannot distinguish them. Keep it to that one attribute.

### `ItemRowActions.tsx` — client

Pin, favorite, delete. Calls `toggleItemPinned` / `toggleItemFavorite` directly, ideally
with `useOptimistic` so a star responds instantly. Delete goes through a confirm step —
follow `DeleteAccountForm`'s ordering convention, where on a destructive form the safe
choice takes the first position (`ChangePasswordForm.tsx:117-119` documents the rule).

### `ItemsEmptyState.tsx` — server

Type icon in `type.color`, a line naming the type's `label`, a create button.
Type-agnostic — everything it shows comes off the `ItemType` row.

### Component summary

| Component | Env | Knows about type? |
|---|---|---|
| `ItemList` | server | Only `label`/`icon`/`color` (data) |
| `ItemCard` *(existing)* | server | Only `label`/`icon`/`color` (data) |
| `ItemDrawer` | client | No |
| `ItemForm` | client | No — passes `contentKind` through |
| `ItemContentFields` | client | **Yes — the one `switch`** |
| `ItemRowActions` | client | No |
| `ItemsEmptyState` | server | Only `label`/`icon`/`color` (data) |

## 8. Missing dependencies

The forms above need shadcn components that are **not installed**. Present:
`avatar, badge, button, card, collapsible, dropdown-menu, input, label, separator,
sheet, sidebar, skeleton, tooltip`.

| Needed | For |
|---|---|
| `textarea` | `content` on all four TEXT types |
| `select` | language picker, collection picker |
| `dialog` | delete confirmation (or reuse `sheet`) |
| `sonner` | *Optional now.* The standards doc used to mandate toasts for errors; it now specifies inline errors, which every existing form already renders. A toast is a deliberate addition, not a prerequisite. |
| `checkbox` / `switch` | pin and favorite in the form |

Add with `npx shadcn@latest add textarea select sonner checkbox`. Note
`components.json` pins `"style": "radix-nova"`, so the additions match the existing
look automatically.

No Markdown editor or syntax highlighter is installed either. The project overview
promises both (§3E "Markdown editor for text-based types", §7 "Syntax highlighting on
all code blocks"), and neither is in `package.json` — a decision to make before the
TEXT branch of `ItemContentFields` can be built.

## 9. Pro gating and plan limits — one seam

`file` and `image` are Pro (`src/lib/pro.ts`), and the free plan caps items at 50 and
collections at 3 (`context/project-overview.md` §6). **Everything is currently
unenforced** — `isProItemType` only renders a badge
(`SidebarTypeNav.tsx:68`), and the project overview is explicit that gating should be
*"a config flip at launch, not a rebuild."*

Build one seam now, called from `createItem` and nowhere else:

```ts
/** Null when allowed, a user-facing sentence when not. */
async function checkPlanLimits(
  userId: string,
  itemType: { name: string },
): Promise<string | null>;
```

Today it returns `null` unconditionally. At launch it reads `User.isPro` and the item
count. One call site, one function, no rebuild — and critically, the check belongs in
the **action**, not the component: a hidden "New Item" button is not enforcement, for
the same reason the proxy is not authorization.

## 10. Build order

> **Steps 1–4 shipped** as the `feature/item-list-view` branch. What landed differs from
> the sketch in three ways: the segment is **`[slug]`**, not `[type]` (§11's first open
> question, resolved — the column is called `slug` and both existing links already built
> one); `getItemTypeBySlug` returns the plain `ItemTypeSummary` rather than a wider select,
> because the list page needs no `contentKind` — the wider select in §4 is still the right
> call for the form, whenever it is built; and no `ItemList`, `ItemsEmptyState` or
> `not-found.tsx` was created, since the page's header and empty state are a few lines each
> and Next's default not-found page already answers an unknown slug. `getItem` is not built.

1. ~~**`src/proxy.ts`** — add `/items/:path*`. Nothing else works until this lands.~~ **Done.**
2. ~~**`src/lib/db/item-types.ts`** — `getItemTypeBySlug`.~~ **Done**, wrapped in React `cache()` and ordered `isSystem DESC`, since `@@unique([userId, slug])` lets a custom type reuse a system slug.
3. **`src/lib/db/items.ts`** — ~~`getItemsByType` (a `where` addition + wrapper)~~ **done, exactly the one-line `where` addition predicted**; `getItem` still to build.
4. ~~**`src/app/(app)/items/[type]/page.tsx`**~~ **Done** at `[slug]`. The seven sidebar links no longer 404.
5. **`src/lib/item-schemas.ts`** — the discriminated union.
6. **`src/actions/items.ts`** — `createItem` / `updateItem` / `deleteItem` / toggles.
7. **shadcn additions** — `textarea select sonner checkbox`.
8. **`ItemDrawer` + `ItemForm` + `ItemContentFields`** — TEXT and URL branches only. That covers snippet, prompt, command, note and link: **five of seven types, 18 of 18 seeded items.**
9. **FILE branch** — needs the R2 upload route and Pro gating; deliberately last.

Steps 1–4 are a shippable read-only slice with no new dependencies, which is what makes
them the right first branch under `context/ai-interaction.md`'s one-feature-per-branch
workflow.
