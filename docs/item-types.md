# Item Types

Reference for the seven system item types Devstash ships with — what each one is
for, how it is stored, and how it renders.

> Generated by `/research item-types-research`. Sources: `context/project-overview.md`,
> `prisma/schema.prisma`, `prisma/seed.ts`, `src/lib/icons.ts`, `src/lib/pro.ts`,
> `src/lib/db/item-types.ts`, `src/lib/db/items.ts`, `src/lib/db/collections.ts`, the
> `src/components/dashboard/` cards, and a live read of the Neon **development** branch.
>
> The research prompt listed `src/lib/constants.tsx` as a source. **That file does not
> exist** — there is no central constants module. Type metadata lives in the database
> (`ItemType` rows, seeded by `prisma/seed.ts`); the only code-side lookups are the icon
> map in `src/lib/icons.ts` and the Pro list in `src/lib/pro.ts`.

---

## 1. Where a type actually lives

An item type is a **database row**, not a TypeScript constant. `ItemType`
(`prisma/schema.prisma:93-121`) carries every display and routing attribute:

| Column | Purpose | Example |
|---|---|---|
| `name` | Stable identifier — never shown to users, safe to branch on | `snippet` |
| `label` | Plural display name in the UI | `Snippets` |
| `slug` | Route segment behind `/items/[slug]` | `snippets` |
| `icon` | Lucide icon name, resolved through `getIcon()` | `Code` |
| `color` | Free-form hex, drives borders/tiles inline | `#3b82f6` |
| `contentKind` | `ItemContentKind` enum the type produces | `TEXT` |
| `isSystem` | `true` for the seven built-ins; system types are immutable | `true` |
| `userId` | `null` for system types, set for future custom types | `null` |

Two consequences worth knowing:

- **`name` is the branch key, not `label` or `slug`.** `src/lib/pro.ts:10` keys the Pro
  set off `name` precisely because a label or slug can be reworded without changing what
  the row *is*.
- **Uniqueness is not enforced for system types.** Postgres treats `NULL`s as distinct in
  a unique index, so `@@unique([userId, name])` and `@@unique([userId, slug])` only
  constrain *custom* types. `seedSystemItemTypes()` (`prisma/seed.ts:66-88`) guards the
  seven system rows in application code with an explicit `findFirst` + `update`/`create`
  instead of `upsert`.

## 3. Summary: text vs. file vs. URL

`ItemContentKind` (`prisma/schema.prisma:87-91`) has exactly three members, and it is
denormalized onto both sides of the relation: `ItemType.contentKind` declares what a type
produces, `Item.contentType` records what an individual item stores.

| Content kind | Types | Populated columns | Null columns |
|---|---|---|---|
| `TEXT` | snippet, prompt, command, note | `content`, optionally `language` | `url`, `fileUrl`, `fileName`, `fileSize` |
| `URL` | link | `url` | `content`, `language`, all file columns |
| `FILE` | file, image | `fileUrl`, `fileName`, `fileSize` | `content`, `language`, `url` |

**4 text / 1 URL / 2 file.** Note the asymmetry: the storage columns are all nullable and
nothing in the schema enforces the mapping — `contentType` is a plain enum column, not a
discriminated union. The seed encodes the mapping in a lookup table
(`CONTENT_KIND_BY_TYPE`, `prisma/seed.ts:440-445`); any write path must set
`Item.contentType` to match its `ItemType.contentKind` itself.

**`language` is only meaningful within `TEXT`**, and only for the code-like types. In the
seed, snippets and commands set it; prompts and notes do not.

## 4. Shared properties

Every item, regardless of type, carries the same envelope (`Item`,
`prisma/schema.prisma:123-158`):

- **`title`** — required, the only mandatory content field.
- **`description`** — optional one-liner, rendered under the title on the card.
- **`isFavorite` / `isPinned`** — booleans, each with its own composite index
  (`@@index([userId, isPinned])`, `@@index([userId, isFavorite])`) because the dashboard
  filters on them per user.
- **`tags`** — many-to-many via `ItemTag` → `Tag`. Tags are **per-user**
  (`@@unique([userId, name])`), not global.
- **`collections`** — many-to-many via `ItemCollection`. A collection holds items of *any*
  type; one item can live in several collections.
- **`createdAt` / `updatedAt`** — `updatedAt` is the sort key for both the recent-items
  and recent-collections lists.
- **`userId`** — every item is owned; deletion cascades from `User`.
- **`itemTypeId`** — required, so an item **always** has a type. `Item.itemType` is a plain
  FK with no `onDelete`, which is part of why system types are immutable.

Type is therefore purely about *content shape and presentation*. Favoriting, pinning,
tagging, collection membership and search behave identically across all seven.

## 5. Display differences

The surprising finding: **there is very little per-type branching in the UI.** Because
`icon` and `color` are data, one component renders every type.

### What is shared

`ItemCard` (`src/components/dashboard/ItemCard.tsx`) renders all seven identically:

- A **left border** at 4px in `type.color` (inline style — the colors are free-form hex,
  so they cannot be Tailwind classes).
- A **9×9 rounded tile** with the type icon, background `${type.color}1a` (`1a` = 10%
  alpha) and foreground `type.color`.
- Title, pin marker, favorite star, `updatedAt`, description, tag badges.

The icon itself comes from `TypeIcon` → `getIcon()` (`src/lib/icons.ts:30-32`), which
looks the Lucide component up in an **explicit eight-entry map** rather than off the
`lucide-react` namespace, so the bundler only ships what is used. Unknown names fall back
to the generic `File` icon — which is what a future custom type with an unmapped icon
would render as. (The map includes `FileText`, which no system type currently uses.)

### What differs by type

| Surface | Per-type behavior |
|---|---|
| Sidebar "Types" nav | Row per type, icon tinted `type.color`, links to `/items/{slug}`, badge with the user's item count. **`file` and `image` additionally get a `PRO` outline badge** — the only hard-coded per-type branch in the UI (`SidebarTypeNav.tsx:68`, via `isProItemType`). |
| Collection card border | Takes the color of the collection's **dominant** type — the type most of its items use, computed by a grouped raw SQL count, falling back to `Collection.defaultType` for an empty collection (`src/lib/db/collections.ts:144-190`). |
| Collection card footer | One icon per type the collection holds, most-used first, ties broken on `label`. |
| Type list page | `/items/[slug]` renders every item of one type in a responsive grid of the same `ItemCard`, so it too is type-agnostic — the only per-type things on it are the header's icon and color, both read off the row. |
| Item detail rendering | **Not built yet.** There is no per-item route or drawer; the list page's cards are not yet links. Per the project overview, text types will get a Markdown editor and syntax highlighting, `link` a URL field, and `file`/`image` an upload control, all inside a slide-out drawer. |

### Ordering

`getItemTypes()` (`src/lib/db/item-types.ts:47-65`) orders
`isSystem DESC, createdAt ASC, label ASC`. `ItemType` has no sort column, so system types
lead and each group falls back to insertion order — meaning the sidebar order is exactly
the seed array's order: **snippet, prompt, command, note, file, image, link**. `label` only
breaks ties between rows written in the same instant.

Counts in the nav are scoped to the current user (`_count: { items: { where: { userId } } }`),
so a system type shared by every account still reports only that user's items, and reports
`0` for an unused type — which the nav still lists.

## 6. Pro gating

`file` and `image` are Pro-only per `context/project-overview.md` §6. This is a **product
decision, not a per-row fact**, so `ItemType` carries no column for it — the list lives in
`src/lib/pro.ts:10` as a `Set` keyed on `name`.

Gating is **display-only during development**. `isProItemType()` renders the `PRO` badge
but nothing blocks a non-Pro user from filing an item under those types. The seeded demo
user has `isPro: false`.

`image` are currently reachable only through the (not-yet-built) create UI.

## 8. Custom types (post-MVP)

The schema already supports them: set `userId` and leave `isSystem: false`. The
`@@unique([userId, name])` / `@@unique([userId, slug])` constraints do real work for these
rows (unlike system types), and `getItemTypes()` already returns
`WHERE userId IS NULL OR userId = :userId`, so a custom type would appear in the sidebar
with no query change.

What would need building: a creation UI, validation that `slug` does not collide with a
system type's route, restricting `icon` to the names `getIcon()` knows, and a decision on
whether `color` stays free-form hex or becomes a fixed palette — still listed as an open
question in `context/project-overview.md` §4.2.
